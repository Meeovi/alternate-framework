# Architectural Rules for M Framework: Backend-Agnostic Engine

## Context & Principles
The M Framework is a highly modular, backend-agnostic ecosystem built on **Nuxt 4 Layers** and orchestrated via an **adapter-gateway (GraphQL Mesh)**. 

To prevent fragile, bloated, or overengineered AI code, you must strictly follow the data-isolation boundaries defined below. The goal is to keep the frontend layers completely blind to the specific underlying backend implementations (e.g., Medusa, Magento, BuddyPress).

---

## 1. Core Mandates (The Guardrails)
* **DO NOT** write custom client-side data normalizers or mapping utilities using heavy JavaScript or `any` types.
* **DO NOT** create unique REST or standalone fetch utility endpoints (e.g., vanilla `fetch('/api/feature')`) for backend logic.
* **DO** leverage the unified **GraphQL Mesh schema contract** upstream for structural data changes.
* **DO** utilize strong typing by generating code from schema operations using compile-time type schemas (`.graphql` queries/mutations).
* **DO** prioritize declarative architecture over custom procedural pipelines.

---

## 2. Structural Separation of Concerns

### A. Data Layout Variations (Gateway Layer)
If a backend swap requires handling differing data shapes or properties (e.g., Medusa returns `thumbnail` while Magento returns `small_image`), **do not fix this in the frontend components.** * Enforce polymorphism using GraphQL **Interfaces** or **Unions** directly inside the `adapter-gateway` schemas.
* The frontend must query the generic interface field using inline fragments (`... on BackendType`).

### B. Pipeline/Execution Variations (Driver Strategy Pattern)
If a business operation requires a completely distinct mutation or execution payload structure based on the active provider, use a **Strategy Pattern** managed via `alternate-sdk` drivers:

1. **Define a strict TypeScript contract** interface inside the shared schema.
2. **Implement dedicated driver objects** that execute the generated type-safe operations.
3. **Inject the active driver dynamically** via a Nuxt application plugin matching environment parameters.

---

## 3. Reference Implementation Standard

### Incorrect Approach (Fragile AI Anti-Pattern)
Avoid generating imperative CRUD files that mask structural discrepancies through manual JSON typing:
```typescript
// ❌ ANTI-PATTERN: Loosely typed REST wrapper bypassing the gateway
export const useFeature = () => {
  const save = async (data: any) => {
    return await fetch('/api/custom-endpoint', { method: 'POST', body: JSON.stringify(data) })
  }
  return { save }
}
Correct Approach (Production-Grade Agnostic Standard)
Implement decoupled drivers with clean compilation boundaries:

This is an example implementation:

TypeScript
// 1. Agnostic Driver Definition (~/shared/types/drivers.ts)
export interface FeatureDriver {
  execute(name: string, payload: Record<string, any>): Promise<{ id: string; success: boolean }>;
}

// 2. Headless Driver Instance (~/alternate-sdk/drivers/medusa-driver.ts)
import type { FeatureDriver } from '~/shared/types/drivers'

export const MedusaFeatureDriver: FeatureDriver = {
  async execute(name, payload) {
    // Relying strictly on autogenerated GraphQL client operations
    const { data } = await useGqlCreateMedusaEntity({ name, config: payload })
    return { id: data.id, success: true }
  }
}

4. Execution Workflow for Kilo AI
When asked to adapt or refactor an existing architecture component:

Identify if the requested logic variation is structural data (resolve via Gateway GraphQL schemas) or operational behavior (resolve via SDK Strategy Drivers).

Ensure no Vue or Nuxt component directly references a backend-specific platform keyword.

Always verify that components rely on generated types instead of implicit runtime structures or properties.
